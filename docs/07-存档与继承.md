> 代码：`core/SaveManager.ts`（927 行）· `core/LevelFlow.ts`（1147 行）· `data/GameTypes.ts`

## 一、存档键位

| 键名 | 数据结构 | 写入时机 | 读取时机 |
|---|---|---|---|
| `mg_profile` | `PlayerProfile` | 解锁关卡 / 成就 / 图鉴 / 抽卡 / 升阶 | 主界面、任何面板 |
| `mg_level` | `LevelState` | 关卡内每次数据变动 | 启动时判断可否续玩 |
| `mg_archive_<levelId>_<tier>` | `LevelArchive` | **通关时覆盖写入** | 进入该关该难度时判断是否弹选择面板 |

**关卡 × 难度双主键**（`mg_archive_3_2` = 第 3 关困难档案，
统计键 `"3_2"`）。

### 为什么必须按难度分开存

第 3 关的普通和噩梦是两个完全不同的挑战。混在一个键里，
玩家打完噩梦回头看会发现普通难度的最高分被覆盖了 ——
纪录直接失效，"刷新纪录"这个复玩核心驱动也就废了。

> 📌 `KEY_ARCHIVE_PREFIX_LEGACY` 与新前缀**字符串完全相同**（都是 `'mg_archive_'`），
> 靠 `_tier` 后缀区分。历史文档暗示两者不同。

## 二、签名机制

每条记录包一层 `{ data, sig, ts }`：

```ts
sig = fnv1a(SALT + stableStringify(data) + SALT)
```

**`stableStringify` 必须按 key 排序。** 用原生 `JSON.stringify` 会因对象 key 插入顺序不同
产生不同字符串，导致签名误判 —— 这是最容易被忽略的一个坑。

### ⚠️ 校验失败会删档

签名不匹配时**直接 `removeItem` 删除该条记录**并降级为无档案状态
（`SaveManager.ts:99-101`），不会把可疑数据喂给游戏逻辑。

这个设计偏激进：如果某个版本的 `stableStringify` 实现变了，
或 `SALT` 变了，**所有老存档会被静默清空**。见 `12-缺口与风险.md`。

## 三、版本迁移链（`SAVE_VERSION = 8`）

实际存在的迁移函数只有 5 个：

| 函数 | 触发 | 做了什么 |
|---|---|---|
| `migrateToV2` | `fromVersion < 2` | 补难度维度：`mg_archive_3` → `mg_archive_3_1` |
| `migrateToV3` | `fromVersion < 3` | 形态图：`{id, stage}` → `{formId, kind, exp, lv}` |
| `migrateToV6` | `fromVersion < 6` | 品阶吸收 rank：老 `rank` 映射成品阶 |
| `migrateToV7` | `fromVersion < 7` | 防具改四部位实例模型 + 补 `tutorials` |
| `migrateToV8` | `fromVersion < 8` | 补 `omni: { stage: 0 }`（万象线进度） |

> ⚠️ **`migrateToV4` 与 `migrateToV5` 函数不存在。** v4/v5 只有内联兜底
> （`SaveManager.ts:269` 注释自证）。历史文档把 v4→v5、v5→v6 描述成独立迁移步骤，
> 实际是 v3→v6 一步跳过去的。

### 3.1 v1 → v2：补难度维度

```
mg_archive_3      → mg_archive_3_1   （原始字符串直接搬运，签名依然有效）
bestScores["3"]   → bestScores["3_1"]
maxTiers          → 所有已解锁关卡补 1
globalMaxTier     → 1
```

**搬运的是原始 localStorage 字符串而不是重新序列化**，所以老数据的签名不会被破坏，
迁移是原子且无损的。

### 3.2 v2 → v3：形态图反查

老档案只有 `(id, stage)`，需要反查成 `formId`：

```ts
{ equipStates: [{ id: 'blade', stage: 2 }] }
  → { loadout: [{ formId: 'blade_rift', kind: 'weapon', exp: 0, lv: 3 }] }
```

靠 `evolveTo` 数组的**第一项是主线**这条约定逐级走 ——
这也是形态表里 `evolveTo` 顺序不能随意调的原因。

### 3.3 v5 → v6：品阶吸收 rank

三条原则：

1. **老 rank 映射成品阶，不清零** —— `rarity = rank - 1`（rank 1→青铜，rank 5→史诗）。
   老玩家为 rank 投入的材料与金币一笔勾销是最伤玩家的迁移方式。
2. **不补到神话/传说** —— 凭空映射上去等于跳过整套品阶内容。老玩家迁移后最高到史诗。
3. **镶嵌槽只增不减** —— `forgeOf()` 保证长度只增不减，老玩家保底保留原有石头。
4. **不白送任何新材料** —— 水晶保留原值、碎片与祝福值从 0 开始、辅助从 `seenForms`
   回填但一律 1 阶。

> ⚠️ **破防公式因此产生语义漂移**：`BREAK_PER_RANK` 的常量名与"满阶突破（5 阶）"的注释
> 都还是 rank 时代的，但 rank 已删、现在传的是 `rarity + 1`。
> 实际破防上限因此变成 0.60 而非文档写的 0.48。见 [05-属性与锻造 §4](05-属性与锻造.md)。

### 3.4 v6 → v7：防具改四部位

- 旧 `armor.owned`（`string[]` 或旧 `OwnedArmor{id,rarity}`）与 `worn: string` 退役
- 旧单件防具 id（`armor_fire` / `armor_omni` 等）**直接清退**（属不同模型，无等价映射）
- 新结构：`owned` 赋 `uid`，`worn` 置 `null`
- 老档防具补齐品阶基础孔

### 3.5 v7 → v8：补万象线进度

```ts
p.omni = { stage: 0 };   // 只补结构，不发全属性石、不发万象套
```

坏档兜底：`'abc'` → 0、`99` → 4（clamp）、`-5` → 0。

## 四、继承：白名单与结构收敛

### 4.1 为什么不是"跨关继承"

| | 跨关继承（❌ 不是本作方案） | 同关复玩继承（✅ 本作方案） |
|---|---|---|
| 数据流向 | 第 N 关 → 第 N+1 关 | 第 N 关 → **只在第 N 关** |
| 档案键 | 全局一份 run | `levelId × tier` 维度，每关一份 |
| 消费者 | 下一关的开局 | 本关的下一次开局 |
| 进度关系 | 数值与进度耦合 | 数值与进度**解耦**（重置数值不影响解锁进度） |

**第 N 关通关后进入第 N+1 关，第 N+1 关一定从初始数据开局。**
第 N 关的装备被封存在该关档案里，只有玩家回头重打第 N 关时才可能被取出。

### 4.2 白名单 `CARRY_WHITELIST`

```ts
// data/LevelConfig.ts:38-41（不在 SaveManager！）
export const CARRY_WHITELIST: string[] = [
    'coin', 'gem',                    // 可继承资源
    'atk', 'hp', 'critRate', 'speed', // 可继承属性
];
```

**只有 6 个键。** 放在白名单外的数值**永远不会进入档案**。

典型应该排除的字段：

- 关卡专属钥匙 / 通行证 —— 下一关的关卡结构不同，带过去会卡死
- 一次性强力增益（如"本关无敌 10 秒"）—— 带进复玩会破坏关卡设计意图
- 临时 Buff 计时器 —— 语义上属于"本关状态"，不属于"装备"

`CARRY_RATE = 1.0`（全量继承）。

> 📌 历史文档把 `CARRY_WHITELIST` 的代码块写在《继承机制设计》里，
> 实际定义在 **`data/LevelConfig.ts:38`**，`SaveManager` 只在注释提及、无 import。

### 4.3 装备的结构收敛

`buildLoadout`（`LevelConfig.ts:260-324`）对装备做一次收敛：

```ts
const clip = (st, kind) => {
    let formId = st.formId;
    if (!formId) formId = kind === 'weapon' ? legacyFormId(st.id, st.stage) : st.id;
    let depth = st.stage || 0;
    try { depth = requireForm(formId).depth; }
    catch (e) { formId = kind === 'weapon' ? legacyFormId(st.id, 0) : st.id; depth = 0; }
    equipment.push({ id: st.id, formId, kind, stage: Math.max(0, depth), exp: Math.max(0, Math.floor(st.exp)) });
};
```

即使有人把存档改成 `stage: 999`、或填一个不存在的 `formId`，
读回来只会被夹到合法区间或**整条丢弃**（`requireForm` 抛错 → 退回根形态）。
"宁可让玩家掉一层形态，也不能让一个不存在的形态进入战斗。"

天赋也做收敛：只保留 `> 0` 的整数层数。

### 4.4 继承匹配按"武器线"而非 id

`createRunLoadout` 按形态所属武器线（`sources` 含这件武器）匹配，不是按 id 精确匹配 ——
老档里可能存着合成形态（id 是材料第一件、formId 是 `fus_*`），精确匹配会让继承直接失效。

## 五、同关复玩的三个时序

### 5.1 首次挑战第 3 关（无档案）

```
LevelSelectPanel.onLevelClicked(3)
  → LevelFlow.openLevel(3)
      → SaveManager.loadArchive(3, 1) === null
      → startFresh(3, 1)
          → enterLevel(3, null, carried=false)
              → state.stats = cfg.initialStats
```

### 5.2 第 3 关通关

```
GameEntry.onBattleWin()
  → LevelFlow.onLevelClear()
      → state.cleared = true
      → buildLoadout(state)          ← 白名单裁剪 + 形态收敛在这里发生
      → SaveManager.addGold()        ← 发放永久金币（复玩打 6 折）
      → SaveManager.saveArchive()    ← 覆盖 mg_archive_3_1
      → SaveManager.unlockLevel(4)
      → EquipmentManager.syncProfile()
      → phase = 'SETTLE'
```

### 5.3 回头重打，选择继承

```
LevelSelectPanel.onLevelClicked(3)
  → openLevel(3) → 有档案 → phase='LOADOUT' → emitLoadout()
      → LoadoutPanel.show()  逐件显示"铁剑 → 裂空剑　攻击 +160%　范围剑气"
      → AdReward.preload(CARRY_OVER)

玩家点「看视频 · 继承装备开局」
  → LevelFlow.startWithCarry(3, 1)
      → AdReward.show() → isEnded === true 才算成功
      → SaveManager.bumpAdView()
      → enterLevel(3, archive.loadout, carried=true, source='archive')
          → Object.assign(state.stats, loadout.stats)      ← 数值 100% 继承
          → createRunLoadout(equippedIds, loadout.equipment, loadout.talents)
```

## 六、两种继承，两种成本

**这是本体系最容易做错的地方。**

| 场景 | 是否继承 | 成本 | 原因 |
|---|---|---|---|
| **首次进入更高难度** | **默认继承** | **免费** | 噩梦敌人血量 ×3.3、数量 ×1.6，而玩家带的是未进化的**根形态** —— 不给继承纯属劝退 |
| **同一难度复玩** | 看激励视频 | 一次广告 | 此时玩家要的是"冲更高纪录"，带巅峰装备重来的动机最强 |

### 为什么跨难度继承不能做成广告位

看起来"看广告才能打高难度"能显著提高 eCPM，但它会带来三个问题：

1. **提审风险**：把游戏机制（难度推进）做成广告门槛，容易被判定为**强制观看广告**。
2. **流失**：玩家打到困难关卡住 → 需要看广告才能继续 → 但看广告本身不能提升数值
   → 看完还是打不过 → 直接卸载。
3. **体验断裂**：难度递进应该是"我变强了所以能打更难"，而不是"我付了广告费所以能打更难"。

**广告的位置应该留在玩家已有明确动机的地方（刷纪录），而不是卡住玩家的地方。**

### 同一难度复玩走广告，成本是否合理

合理，因为两个选项对玩家都是净收益：

- 看广告 → 带巅峰装备开局，冲纪录（明确收益）
- 重新开始 → 从初始装备开局，档案**保留**（没有损失）

## 七、"重新开始"不删档

```ts
DROP_ARCHIVE_ON_RESTART = false
```

玩家点「重新开始」的动机绝大多数是"我想再玩一遍"，而不是"我要毁掉我的装备"。
一旦真删档，玩家会愤怒，而且下次还得从头刷 —— 体验代价远大于那一点广告转化收益。

想真正清档走 `resetArchive()` 显式入口（已接到关卡选择界面的重置按钮）。

放在代码里的理由：

- 玩家不会因为好奇点一下按钮就永久损失进度
- 广告的转化压力转移到了"我想变强"这个**正向动机**上，而不是"我怕丢东西"这个负向动机上，提审时也更安全

## 八、复玩加难

### 8.1 档位

```ts
REPLAY_BOOST_STEPS = [0, 0.15, 0.30, 0.50, 0.80, 1.20]   // 6 档，最大 +120%
REPLAY_BOOST_MAX = 3.0
```

**已通关过的难度**在真正进场前会多一步：复玩加难面板。
第一次打进某档难度时**不问**（加了是劝退）。

### 8.2 为什么第一档永远是"不加难"

有些玩家重进只是想补成就、试试新武器、或者单纯爽一把。
强制加难会把这些人挡在外面。**加难是主动的风险定价，不是门槛。**

### 8.3 为什么必须提前给出数值

加难不是模糊的"更难一点"，面板上直接写"+30% 会让血量从 220 涨到 286"。
**把代价藏起来再加难，玩家只会觉得被暗算。**

加难同时抬高金币收益（`(1 + boost × 0.8)` 与结算期 `1 + boost × 0.5`），
所以它不只是找苦吃，而是主动拉高收益曲线 —— 这是"再来一局"这个按钮真正的钩子。

### 8.4 加难对敌人的作用范围

| 量 | 加难影响 |
|---|---|
| 敌人数量 | `× (1 + boost × 0.5)` —— **只加一半权重**，避免变成纯人海 |
| 敌人血量 / 攻击 | `× (1 + boost)` |
| 远程怪比例 | `+ boost × 0.06` |
| 金币产出 | `× (1 + boost × 0.8)`（关卡配置）+ 结算期 `× (1 + boost × 0.5)` |
| 经验 | 无影响 |

## 九、防作弊现状

### 已经做到的

- `stableStringify` 按 key 排序后签名，杜绝 key 顺序导致的误判
- 读档时校验不通过直接删除该条记录并降级，不把可疑数据喂给游戏逻辑
- `buildLoadout` 对形态按配置表上限收敛，`stage: 999` 无效
- 白名单机制从结构上限制了能进档案的字段

### 🔴 还没做到的

**本地存档可被修改。** 加盐哈希能挡住普通修改器，但小游戏包体最终可被反编译，
盐值理论上能挖出来。文档自承的云端校验 / 服务端档案 / 异常检测三项方案
**全部未实现**。目前只有加盐签名 + 结构收敛。

**进阶方案（按成本排序）**：

1. **关键数值云端校验**：微信云开发，通关时上报 `{levelId, score, loadoutHash}`，
   对异常值标记但不硬拦（避免误伤）。
2. **服务端下发档案**：`loadout` 完全托管云端，本地只存引用 ID。防作弊最强，
   但强依赖网络。
3. **数值异常检测**：本地做合理性检查（如 `stats.hp` 超过理论最大值 3 倍直接判篡改）。
   零成本，能挡住大部分粗暴修改。

## 十、LevelFlow 状态机

### 10.1 Phase 列表

| Phase | 含义 | 显示战斗层 |
|---|---|---|
| `SELECT` | 主界面 / 关卡选择 | — |
| `LOADOUT` | 继承选择面板 | — |
| `REPLAY_BOOST` | 复玩加难面板 | ❌ **不显示** |
| `PLAYING` | 战斗中 | ✅ |
| `REWARD` | 三选一 | ✅ **显示** |
| `SETTLE` | 结算 | — |

> ⚠️ 历史文档说"LOADOUT → REPLAY_BOOST 直接流转"—— 实际加难闸门在 `beginEntry` 内，
> 由 `openLevel` 的分支或 `startWithCarry` 进入，不是简单的线性流转。

### 10.2 战败后的处理

`retryLevel()`（`GameEntry.ts:397`）**保留**本关数据与进化进度 ——
注释说明理由："不该有任何惩罚"。战败也会调 `reportElementStats()`（记录属性统计）。

### 10.3 三选一的确定性种子

```ts
seed = levelId × 7919 + difficulty × 1313 + loadout.level × 17 + _rewardSeq
```

确定性防"重开刷卡"。
