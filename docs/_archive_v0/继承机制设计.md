# 同关复玩继承机制 · 设计说明

## 一、为什么不能做成「跨关继承」

两种模型看着像，实现与数据结构的差别很大，先明确边界：

| | 跨关继承（❌ 不是本需求） | 同关复玩继承（✅ 本方案） |
|---|---|---|
| 数据流向 | 第 N 关数据 → 第 N+1 关 | 第 N 关数据 → **只在第 N 关** |
| 档案键 | 全局一份 run | `levelId` 维度，每关一份 |
| 消费者 | 下一关的开局 | 本关的下一次开局 |
| 进度关系 | 数值与进度耦合 | 数值与进度**解耦**（重置数值不影响解锁进度） |

本方案里，第 N 关通关后进入第 N+1 关，**第 N+1 关一定从初始数据开局**。第 N 关的装备被封存在该关档案里，只有玩家回头重打第 N 关时才可能被取出。

## 二、存档键位设计

| 键名 | 数据结构 | 写入时机 | 读取时机 |
|------|----------|----------|----------|
| `mg_profile` | `PlayerProfile` | 解锁关卡 / 成就 / 图鉴 / 复玩设置 | 关卡选择界面 |
| `mg_level` | `LevelState` | 关卡内每次数据变动 | 启动时判断可否续玩 |
| `mg_archive_<levelId>_<tier>` | `LevelArchive` | **通关时覆盖写入** | 进入该关该难度时判断是否弹选择面板 |

> v2 的键是 `mg_archive_<levelId>`（没有难度维度），
> 与之配套的统计键是 `"3"` 而不是 `"3_1"`。
> v3 迁移时把老键统一改写成 `mg_archive_3_1` / `"3_1"`，
> 玩家的通关记录与最高分一条不丢。

每条记录都包一层 `{ data, sig, ts }`，`sig = fnv1a(SALT + stableStringify(data) + SALT)` 多轮混淆。签名不匹配时直接删除该条记录并降级为无档案状态，**不会**把可疑数据喂给游戏逻辑。

> `stableStringify` 必须按 key 排序。用原生 `JSON.stringify` 会因对象 key 插入顺序不同产生不同字符串，导致签名误判——这是最容易被忽略的一个坑。

## 三、四个关键时序

### 1. 首次挑战第 3 关
```
LevelSelectPanel.onLevelClicked(3)
  → LevelFlow.openLevel(3)
      → SaveManager.loadArchive(3) === null
      → startFresh(3)  ← 无档案，不涉及广告
          → enterLevel(3, null, carried=false)
              → state.stats = cfg.initialStats
```

### 2. 第 3 关通关
```
GameEntry.onBattleWin()
  → LevelFlow.onLevelClear()
      → state.cleared = true
      → 并入 cfg.reward
      → buildLoadout(state)          ← 白名单裁剪 + 进化阶段收敛发生在这里
      → SaveManager.addGold()        ← 发放永久金币（复玩打 6 折）
      → SaveManager.saveArchive()    ← 覆盖 mg_archive_3
      → SaveManager.unlockLevel(4)   → EquipmentManager.syncProfile() 发放新装备
      → phase = 'SETTLE'
```

### 3. 回头重打第 3 关，选择继承
```
LevelSelectPanel.onLevelClicked(3)
  → openLevel(3) → 有档案 → phase='LOADOUT' → emitLoadout()
      → LoadoutPanel.show()  逐件显示"铁剑 → 裂空剑　攻击 +160%　范围剑气"
      → AdReward.preload(CARRY_OVER)

玩家点「看视频 · 继承装备开局」
  → LevelFlow.startWithCarry(3)
      → AdReward.show() → isEnded === true 才算成功
      → SaveManager.bumpAdView()
      → enterLevel(3, archive.loadout, carried=true)
          → Object.assign(state.stats, loadout.stats)          ← 数值 100% 继承
          → createRunLoadout(equippedIds, loadout.equipment,   ← 形态与天赋恢复
                             loadout.talents)
```

注意 `createRunLoadout` 的匹配规则是**按形态所属武器线**（`sources` 含这件武器），
不是按 id 精确匹配 —— 老档里可能存着合成形态（id 是材料第一件、formId 是 `fus_*`），
精确匹配会让继承直接失效。详见 [装备与进化设计.md](装备与进化设计.md)。

### 4. 回头重打第 3 关，先选加难幅度

从 v3 起，**已通关过的难度**在真正进场前会多一步：复玩加难面板。

```
beginEntry(3, tier, data, carried, source)
  → clearCounts["3_1"] > 0 ？        ← 只有打通过的难度才问
      是 → phase = 'REPLAY_BOOST' → emitReplayBoost()
           → ReplayEnhancePanel 弹出，逐档显示敌人血量/攻击/数量
      否 → 直接 commitEntry()        ← 第一次打进这档难度时不问，加了是劝退

玩家选 +30% 并点开始
  → LevelFlow.confirmReplayBoost(true, 0.30)
      → SaveManager.setReplayBoost(3, tier, 0.30)   ← 记住，下次默认选中
      → commitEntry(true, 0.30)
          → getLevelConfig(3, tier, 0.30)           ← 敌人强度按加难重算
          → state.replay = { enabled: true, percent: 0.30 }
```

**为什么第一档永远是"不加难"**：有些玩家重进只是想补成就、试试新武器、或者单纯爽一把。
强制加难会把这些人挡在外面。加难是**主动的风险定价**，不是门槛。

**为什么必须提前给出数值**：加难不是模糊的"更难一点"，
面板上直接写"+30% 会让血量从 220 涨到 286"。
把代价藏起来再加难，玩家只会觉得被暗算。

加难同时抬高金币收益（见 `LevelConfig` 的 boost 结算），
所以它不只是找苦吃，而是主动拉高收益曲线 ——
这是"再来一局"这个按钮真正的钩子。

### 5. 回头看第 3 关，不看广告
```
玩家点「重新开始」
  → LevelFlow.startFresh(3)
      → DROP_ARCHIVE_ON_RESTART = false
      → 【不删档】档案原样保留
      → enterLevel(3, null, false)   ← 装备回到根形态，数值回到初始值
```

**为什么不删档**：玩家点「重新开始」的动机绝大多数是"我想再玩一遍"，而不是"我要毁掉我的装备"。如果这一下就把辛苦攒的装备清空，玩家会愤怒，而且下次进来还得从头刷——体验代价远大于那一点广告转化收益。想真正清档，走 `resetArchive()` 这个显式入口（已接到关卡选择界面的重置按钮）。


## 四、三个必须提前想清楚的设计风险

### 风险 1：继承装备后，这一关变得太简单

这是本机制的结构性矛盾——继承的正是"上次打通这一关时的装备"，所以复玩必然碾压。

**已实现的对策（v3 起，三层叠加）**：

1. **把复玩目标从"通关"改成"冲分 / 计时"**。
   `LevelArchive.bestScore`、`bestTime` 已经在记录，
   `SettlePayload.isNewScoreBest` / `isNewTimeBest` 在结算页做纪录对比，
   关卡选择界面也直接亮出这两个纪录。

2. **复玩加难（玩家自选）**。已通关过的难度在进场前会弹面板，
   让玩家自己选 +0% / +15% / +30% / +50% / +80% / +120%。
   这是比"系统偷偷给敌人加成"好得多的方案：代价是玩家**自己认领**的，
   他不会觉得被暗算；而且他会在"我想试试 +50%"这个目标上主动复玩。

3. **更上级进化只在带老档时出现**。复玩不只是"用更强的装备打同样的怪"，
   而是"多了一条全新的形态路线可以推"。这让复玩有了新内容，而不只是新难度。

**仍在观察的手段**：复玩变体目标（限时挑战 / 无伤通关 / 只用副武器），
让继承只是入场券而不是胜利保证。这个建议先有真机数据再上。

已实现了一部分防刷：复玩时永久金币按 `REPLAY_GOLD_RATE = 0.6` 折算，
避免反复刷同一关攒金币。

### 风险 2：「重新开始」会不会被玩家当成删档

最初的设计是"不看广告就把数据重置"。这在小游戏里是危险的：玩家点「重新开始」的动机绝大多数是"我想再玩一遍"，而不是"我要毁掉我的装备"。一旦真的把档案删了，玩家会愤怒，而且下次还得从头刷。

**已采用的策略：`DROP_ARCHIVE_ON_RESTART = false`** —— 点「重新开始」只是"本次不带装备、从初始装备开打"，档案原样保留，下次进来仍然可以看广告继承。

放在代码里的理由：
- 玩家不会因为好奇点一下按钮就永久损失进度；
- 档案例外的情况（真的想清空）走 `resetArchive()` 显式入口，UI 上单独做，文案明确；
- 广告的转化压力转移到了"我想变强"这个正向动机上，而不是"我怕丢东西"这个负向动机上，提审时也更安全。

如果后续数据显示广告转化率不理想，把 `LevelFlow.DROP_ARCHIVE_ON_RESTART` 改回 `true` 即可，其余逻辑无需改动。但改之前建议先加二次确认弹窗。

### 风险 3：本地存档可被修改

加盐哈希能挡住普通修改器，但小游戏包体最终可被反编译，盐值理论上能挖出来。

**已经做到的**：
- `stableStringify` 按 key 排序后签名，杜绝 key 顺序导致的误判；
- 读档时校验不通过直接删除该条记录并降级，不会把可疑数据喂给游戏逻辑；
- `buildLoadout` 对装备的进化阶段按配置表上限做一次收敛，改档填 `stage: 999` 无效。

**进阶方案（按成本排序）：**
1. **关键数值云端校验**：开通微信云开发，通关时上报 `{levelId, score, loadoutHash}`，对异常值（如第 1 关就打出百万分）标记但不硬拦，避免误伤。
2. **服务端下发档案**：把 `loadout` 完全托管到云端，本地只存引用 ID。防作弊最强，但强依赖网络，首次进入需要等待。
3. **数值异常检测**：本地做一次合理性检查，比如 `stats.hp` 超过理论最大值的 3 倍直接判为篡改。零成本，能挡住大部分粗暴修改。

## 五、白名单机制说明

`CARRY_WHITELIST` 是整个系统的安全阀。放在白名单外的数值**永远不会进入档案**：

```ts
export const CARRY_WHITELIST = [
    'coin', 'gem',                    // 可继承资源
    'atk', 'hp', 'critRate', 'speed', // 可继承属性
];
```

典型应该排除的字段：
- **关卡专属钥匙 / 通行证** —— 下一关的关卡结构不同，带过去没有意义甚至会导致卡死
- **一次性强力增益**（如"本关无敌 10 秒"）—— 带进复玩会破坏关卡设计意图
- **临时 Buff 计时器** —— 语义上属于"本关状态"，不属于"装备"

装备走的是另一条裁剪路径。`buildLoadout()` 里除了白名单，还对装备做了一次结构收敛：

```ts
for (const st of toArchiveStates(state.loadout)) {
    const f = getForm(st.formId);
    if (!f) continue;                                  // 配置表里没有的形态直接丢弃
    equipment.push({
        id: st.id,
        formId: f.id,                                  // ★ 形态 id，v3 新增
        kind: f.kind,                                  // 'weapon' | 'aux'
        // 层级夹在 0~FORM_MAX_DEPTH；同时夹住"合成形态的材料必须都在 sources 里"
        stage: Math.max(0, Math.min(st.stage, FORM_MAX_DEPTH)),
        exp: Math.max(0, Math.floor(st.exp)),          // 经验不得为负
    });
}
```

所以即使有人把存档改成 `stage: 999`、或者填一个不存在的 `formId`，
读回来也只会被夹到合法区间或被整条丢弃。这道收敛是纯本地的、零成本的。

如果后续要加"某类道具可以继承"，只需往白名单加一个 key，其余逻辑无需改动。

## 六、装备在继承里的地位

完整的装备设计见 [装备与进化设计.md](装备与进化设计.md)，这里只强调与继承相关的三点：

1. **局外等级不参与继承**，因为它本来就是永久的。玩家升级装备的钱花出去就永久生效，不随任何关卡重置消失，也不需要看广告。

2. **局内形态与天赋参与继承**，因为它们"只在局内产生"。玩家在关卡里把铁剑养到裂空剑、把天赋叠到 3 层，这本身是这一局的成果；通关后它随档案封存，复玩时才能恢复到那个状态。这条链路正是广告价值的来源。

3. **"更上级进化"只在携带老档时出现**（`EvolutionEdge.advanced`）——
   这是玩家明确要求的一条：

   > "我希望在重复进入的时候添加新的进化路线, 就是只有拿老档进入游戏时候, 会出现更上级的进化,
   >  要不然重复进入没有进化度就没乐趣了"

   实现上是 `LevelFlow.allowAdvanced`，它唯一的判据是
   `state.carrySource !== 'none'`（即本局是否携带了老档）。
   首次开荒拿不到 depth 4 的形态，只有带着上次通关的成果回来才能继续往上走。
   这样"复玩"就有了一个**可见的、新的**目标，而不只是"再打一遍"。

   图鉴面板会把这条路线标成 `★ 复玩解锁的更上级进化` 并写明触发条件，
   让玩家在决定要不要看广告之前就知道"看完广告我能拿到什么"。

## 七、复玩加难的存档字段

`replayBoosts` 与 `replayCounts` 都是 `"<levelId>_<tier>"` 维度的：

| 字段 | 作用 | 为什么不全局存 |
|---|---|---|
| `replayCounts` | 该关该难度的复玩次数 | 第 3 关普通打了 5 次，不代表第 7 关噩梦也打过 5 次 |
| `replayBoosts` | 上次选定的加难百分比 | 加难意愿和关卡强度强相关，不同关的合理档位不同；而且它会被用作下次进入的**默认选中项** |

加难百分比会一路传到 `getLevelConfig(levelId, tier, percent)`，
敌人血量 / 攻击 / 数量三项一起抬升，金币收益同步抬升
（见 [难度体系设计.md](难度体系设计.md)）。
