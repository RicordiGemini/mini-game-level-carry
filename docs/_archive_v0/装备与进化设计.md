# 装备与进化设计（形态图版）

> 本文档描述 **v3** 的装备体系。v2 的"每件装备一条线性进化链"已经被
> **形态图（Form Graph）** 取代，旧文档的 `evolutions[]` / `expToReach` /
> `stage` 等概念全部作废。

## 一、四条互不重叠的成长线

这是整套系统的骨架。四条线的**作用域、消耗品、生命周期完全不同**，
所以从数据结构到 UI 都是分开的，不要混在一起想。

| | 局外升级 | 局内武器形态 | 局内辅助装备 | 局内天赋 |
|---|---|---|---|---|
| 位置 | 主界面 `EquipPanel` | 关卡内三选一 | 关卡内三选一 | 关卡内三选一 |
| 消耗 | 永久金币 `gold` | 占**武器槽** | 占**辅助槽** | **不占任何槽** |
| 产出 | 基础伤害（flat 加算） | 形态跃迁 + 基础伤害并入 | 战斗修正（乘算） | 战斗修正（可叠层） |
| 生命周期 | 永久 | 只在本关，可被档案继承 | 同左，且**进化永不耗槽** | 同左 |
| 上限 | 每件 5 级 | 6 格（复玩 8 格） | 6 格（复玩 8 格） | 每个天赋满层为止 |

### 为什么辅助装备必须"进化不耗槽"

玩家原话：

> "如果升级成功然后进化 可以武器和辅助装备, 这种就不会消失辅助装备"

如果辅助装备也能像武器那样被合成吃掉，玩家会不愿意在局内培养它 ——
因为随时可能"白养了"。所以 `validateFormGraph()` 里有一条硬校验：
**辅助形态只能挂 `upgrade` 边**。配置写错了会在启动时直接报错，
而不是等到线上才让玩家的辅助装备凭空消失。

## 二、形态图：为什么不能再用链

线性链的结构是"第 0 层 → 第 1 层 → 第 2 层 → …"，一件装备一条链，玩家没有选择。

三个具体问题：

1. **没有 build 差异**：所有人的铁剑都长成天罚剑，第 20 局和第 1 局看到的终局是同一把。
2. **无法表达合成**：两件武器合而为一，本质上是一个"多入一"的节点，链装不下。
3. **无法表达"复玩才出现"**：链只有一条，想加一条更上级的只能往后接，那首次开荒也能拿到。

形态图用 `FormNode` + `EvolutionEdge` 表达：

```ts
interface FormNode {
    id: string;                 // 'blade_rift'
    name: string;               // '裂空剑'
    kind: 'weapon' | 'aux';
    equipType: EquipType;       // 局外装备原型（决定基础伤害/射程/间隔）
    sources: string[];          // ★ 血脉来源，见下
    depth: number;              // 0=根形态，4=复玩限定的更上级
    atkPct: number;             // 形态自带的攻击加成
    rangePct: number;
    attackModeId: AttackModeId; // 打出去的形状
    aimModeId: AimModeId;       // 怎么取目标（可覆盖武器类型默认值）
    evolveTo: EvolutionEdge[];
}

interface EvolutionEdge {
    to: string;
    type: 'upgrade' | 'fusion';
    need?: string;      // fusion 时需要的另一件形态
    advanced?: boolean; // ★ 只有携带老档时才出现
    label: string;
    desc: string;
}
```

### `sources` 是这个设计能成立的关键

`sources` 是一个形态的**血脉集合**：

- 根形态：`sources = [自己的 id]`
- 升级形态：继承父形态的 `sources`
- **合成形态：两件材料的 `sources` 并集**

它同时解决了三件事：

1. **合成后基础伤害不亏**
   `baseDamageOfForm(sources)` 把 `sources` 里每件局外装备当前等级的基础伤害**求和**。
   所以"裂空剑 + 暴雨弩 → 剑雨风暴"之后，新形态吃的是两把武器的基础伤害之和 ——
   合成消耗了一个槽位，但战力没有掉，这是"消耗一格"能被接受的前提。

2. **关卡适配不会因进化而失效**
   推荐武器的判定按 `sources` 走（`weaponRootsOf`）。
   玩家把铁剑进化成裂空剑之后，"铁剑是第 1 关推荐武器"这条加成依然生效。
   如果按形态 id 精确匹配，进化一次加成就会莫名消失。

3. **档案继承不会断**
   老档里存的是形态 id，继承时按"形态所属武器线"（`sources` 含这件武器）匹配，
   所以玩家在局外把出战武器从铁剑换成别的，老档里的淬锋剑依然能被正确继承。

## 三、三类进化的行为差异

| | upgrade（升级型） | fusion（合成型） | advanced（复玩限定） |
|---|---|---|---|
| 槽位 | **不消耗** | **消耗一个武器槽** | 同 upgrade 或 fusion |
| 出现条件 | 经验攒够 + 手上有后续形态 | 集齐两件材料 | `carrySource !== 'none'` |
| 实现 | `applyEvolve()` | `applyFusion()` | 只是边的 `advanced` 标记 |
| 数组长度 | 不变 | **-1** | 取决于边的类型 |

### 合成的槽位补偿

合成让武器从 2 件变 1 件，玩家会立刻感到"我亏了"。所以：

```ts
lo.weapons.splice(ib, 1);
lo.pendingPicks += 1;   // ★ 释放出待补选名额
```

`pendingPicks > 0` 时，下一次三选一**强制优先给新武器候选**，
`LevelFlow.chooseReward()` 会**立刻**再开一次三选一，

> 玩家刚做完一个亏格子的决策，应该马上得到补偿，
> 而不是带着空槽再打十几只怪。

玩家原话："如果进化是两个武器合成的进化会消失其中一个武器格子, 可以再选一个武器" ——
这个补偿就是那句话的实现。

### 边界：池子空了怎么办

如果补选时池子已经空了（武器槽满、没有新武器可选），
`openReward()` 会返回 `false` 并**主动把阶段归位到 `PLAYING`**。

这一条是修出来的 bug：原实现只 `return`，阶段就永远卡在 `REWARD`，
战斗停住、面板不弹、玩家只能重启 —— 三选一死锁是最难查的那类线上问题。

## 四、经验与进化节奏

两条曲线吃同一份经验，但用途完全不同：

| 曲线 | 用途 | 门槛函数 |
|---|---|---|
| 关卡等级 `loadout.level` | 触发三选一的节奏 | `levelExpFor(level) = 70 × 1.30^(level-1)` |
| 形态经验 `slot.exp` | 决定哪些槽位可以进化 | `depthExpNeed(depth) = [90, 190, 340, 620, 980][depth]` |

### 为什么进化后要"扣除门槛"而不是"清零"

```ts
function carryExpOver(exp: number, fromDepth: number): number {
    return Math.max(0, Math.floor(exp - depthExpNeed(fromDepth)));
}
```

如果进化后 `exp` 归零，玩家在一局里能推到的深度就完全由击杀数决定，
打得快也推不深 —— 因为每层都从头攒。
扣除门槛后，**溢出的经验会带到下一层**，
于是"清怪快"这件事能直接换成"进化深"。这才是刷分的意义。

## 五、局内三选一

### 候选池的优先级

`RewardPicker` 给每个候选打一个优先级，数字越小越优先：

| 优先级 | 类别 | 条件 |
|---|---|---|
| -2 | 高级合成 | `allowAdvanced`（复玩继承）|
| -1 | 常规合成 | 集齐两件材料 |
| 0 | 进化（升级型） | 经验达标 |
| 1 | 新装备 | 槽位未满 |
| 2 | 天赋 | 永远有货 |

### "固定三选一"与"2 主 + 1 其他"

玩家原话："选武器或者选天赋以及选辅助装备都是固定三选一"。
所以恒产 3 张卡（`REWARD_CHOICES = 3`），组装方式是
**主类别出 2 张、其他类别补 1 张**（`FOCUS_TAKE = 2`）。

主类别按关卡等级轮转（`rewardFocusFor(level) = (level + 1) % 3`），
`+1` 这个偏移是为了让**首次三选一（2 级）落到武器档** ——
新手第一次选卡就看到武器，而不是先看到一堆天赋。

补齐阶段必须**排除主类别**：

```ts
for (const k of otherKinds) {
    if (k === focus) continue;   // ← 不排除的话三张会全同类
    ...
}
```

### 天赋是"永不空屏"的保底

天赋不占槽位、可叠层，所以它不受任何条件约束。
只要还有没满层天赋，三选一就一定能凑齐三张 ——
这保证了"玩家点了升级却什么都没发生"这种情况永远不会出现。

## 六、每关最合适的武器都不一样

### 机制

`LevelAffinity` 给每关配一个**阵型**（`FormationKind`），阵型做两件事：

1. **真的改变刷怪位置分布**（战斗层读同一个阵型枚举摆位）
2. **决定推荐 / 克制武器名单**

两者来自同一张表，所以文案和数值不会互相打架 ——
不会出现"提示说这关适合范围武器，但怪其实排成一列"这种自相矛盾。

| 阵型 | 中文 | 推荐（伤害 ×1.25 · 金币 ×1.30） | 克制（伤害 ×0.80） |
|---|---|---|---|
| scatter | 零散突进 | 单体精准 | 范围武器白给 |
| line | 成列推进 | 贯穿一串 | 只能打一个的 |
| cluster | 密集扎堆 | 范围 / 连锁 | 单体溢出 |
| swarm | 人海散兵 | 高频 / 全屏 | 慢速单体 |

阵型每 4 关循环，但**同一个阵型内部的推荐名单还会按关卡轮转**：

```
第 1 关 零散突进 → 铁剑 + 短弓
第 5 关 零散突进 → 短弓 + 重炮
第 9 关 零散突进 → 重炮 + 铁剑
```

否则"散兵关永远推铁剑+短弓"，玩家打十关看到的建议一模一样，
"每关最合适的武器都不一样"就退化成"每四种阵型里最合适的武器不一样"。

### 刻意不做成硬克制

带推荐 ×1.25、带克制 ×0.80，是"带了明显更爽"，不是"必须带"。
做成硬克制会让泛用户卡关，而这是个微信小游戏，不是硬核 Roguelike。

## 七、数值平衡：怎么调、谁来守

### 有效输出预算模型

每把武器的强度不能只看 `damage / interval`，因为"一次攻击打几个敌人"差别巨大。
`balance_guard.js` 用三个可解释的因子建模：

```
有效预算 = 单发伤害 / 间隔        基础 DPS
         × 一次攻击的期望命中数    打击形状（横扫打多个、单弹打一个）
         × 瞄准可靠度             不索敌的武器会打空，这是操作门槛的代价
```

命中数按 `AttackModeId` 取（近战 1.6 / 横扫 1.8 / 全屏 2.2 / 贯穿 1+0.16×穿透数 / 三连射 1.0 …），
可靠度按 `AimModeId` 取（`FRONT` 0.72 / `MOVE_DIR` 0.80 / 其余 1.00）。

**所有武器的有效预算必须落在中位数的 0.55~1.60 倍之间。**
目前实测区间是 0.80~1.40。

> ⚠️ 三连射必须单独算：`AttackFactory.buildBullet` 里 `count > 1` 时
> **每发**伤害要乘 0.62 再取整，所以真实 DPS 是
> `3 × round(单发 × 0.62) / 间隔`，而不是 `单发 / 间隔`。
> 漏掉 0.62 会把三连射高估约 1.9 倍 —— 曾经据此把飞刃与手里剑
> 一起抬成了全表最高 DPS，被测试挡了下来。

### 几条刻意写死的机制关系

这些不是数值巧合，是有意为之的"定价规则"，也都有测试守着：

| 关系 | 理由 |
|---|---|
| 长枪 FRONT，账面 DPS **必须高于**光矛 LOCK_ON | 光矛不落空，长枪约 1/3 挥击会打空。命中率更高的那把必须更慢 |
| 长枪穿透 5 > 光矛穿透 3 | 贯穿专家是长枪；光矛是"锁定版"，不能连穿透也一起占 |
| 巨镰（SWEEP，半径 `range×0.7`）间隔 **必须长于** 铁剑（近战，半径 `range×0.5`） | 横扫的覆盖面积是近战的 4 倍以上，间隔不拉开就会变成全阵型通用最优解 |

### 为什么不用探针机器人当平衡裁判

试过两种机器人的操作模式，**各有系统性偏差**：

| 模式 | 行为 | 偏差 |
|---|---|---|
| `charge` | 一直朝最近敌人推进 | 把玩家钉在近战距离 → 近战/范围武器恒强 |
| `aggr` | 靠近后掉头撤离 | 射击方向被反复翻转 → 前向/移动向武器恒弱 |

两者给出的武器排名互相矛盾，谁也不能当基准。
所以平衡由**机制模型 + 不变量测试**来守（`balance_guard.js`），
机器人的结论只作为参考线索，不作为断言。

## 八、存档结构（v3）

```ts
interface EquipRunState {
    id: string;       // 局外装备 id
    formId: string;   // ★ v3 新增：当前形态
    kind: 'weapon' | 'aux';
    stage: number;    // = form.depth，冗余存一份方便 UI
    exp: number;      // 距离下一层的进度（已扣过门槛）
}

interface PlayerProfile {
    // … v2 原有字段 …
    achievements: AchievementRecord[];   // 已解锁成就
    seenForms: string[];                 // 进化图鉴
    fusionCount: number;                 // 累计合成次数
    totalKills: number;
    affinityClearCount: number;          // 带推荐武器通关次数
    replayCounts: Record<string, number>; // "3_2" → 复玩次数
    replayBoosts: Record<string, number>; // "3_2" → 已选定的加难百分比
}
```

### v2 → v3 迁移

v2 档案里只有 `(id, stage)`，没有 `formId`。
迁移靠 `legacyFormId(equipId, stage)` 沿 `evolveTo` 的**第一项**反查 ——
这也是"`evolveTo` 数组第一项是主线"这个约定必须被遵守的原因：
迁移规则和图鉴画线规则用的是同一个约定，
才不会出现"存档走的是 A 路线、图鉴画的却是 B 路线"。

## 九、调参速查

| 想改什么 | 改哪里 |
|---|---|
| 武器变强的速度 | `EquipmentConfig.ts` 各武器 `levels[].baseDamage` |
| 武器出手频率 | `EquipmentConfig.ts` 的 `WEAPON_BASE_INTERVAL` |
| 贯穿上限 | `EquipmentConfig.ts` 的 `WEAPON_BASE_PIERCE` |
| 升级贵不贵 | `levels[].upgradeCost` 与 `LevelConfig.goldReward()` |
| 进化快不快 | `FormConfig.ts` 的 `DEPTH_EXP_NEED` |
| 三选一节奏 | `RunConfig.ts` 的 `LEVEL_EXP_BASE` / `LEVEL_EXP_GROWTH` |
| 形态变强多少 | `FormConfig.ts` 里各 `FormNode.atkPct` |
| 槽位上限 | `RunConfig.ts` 的 `WEAPON_SLOT_BASE` / `AUX_SLOT_BASE` / `REPLAY_SLOT_BONUS` |
| 关卡适配强度 | `RunConfig.ts` 的 `AFFINITY_DAMAGE_MUL` / `WEAK_DAMAGE_MUL` |
| 推荐 / 克制名单 | `LevelAffinity.ts` 的 `AFFINITY_POOL` / `WEAK_POOL` |
| 天赋池 | `TalentConfig.ts` 的 `TALENT_TABLE` |
| 成就表 | `AchievementConfig.ts` 的 `ACHIEVEMENT_TABLE` |

改完数值一定要跑 `balance_guard.js` —— 它会告诉你哪一把武器跑出了预算区间。

## 十、加新内容的步骤

**加一把武器**（约 4 步，不需要动架构）：

1. `EquipmentConfig.ts` 的 `EQUIPMENT_TABLE` 加一条（含 `aimMode` / `unlockLevel`）
2. `EquipmentConfig.ts` 的 `WEAPON_BASE_RANGE` / `INTERVAL` / `PIERCE` 各加一项
3. `FormConfig.ts` 的 `WEAPON_ROOT_IDS` 加 id，并写 5 层形态（depth 0~3 常规 + depth 4 复玩限定）
4. 想让它在某关被推荐，往 `LevelAffinity.ts` 的对应 `AFFINITY_POOL` 里加

**加一条合成配方**：往 `FUSION_RECIPES` 加一条，并给产物写一个 `FormNode`。
产物必须有 `depth >= max(材料 depth)` 且 `atkPct > max(材料 atkPct)` ——
"合完反而更弱"会被 `validateFormGraph()` 判为配置错误。

**加一件辅助装备**：同武器，但**只能挂 `upgrade` 边**。

**加一条成就**：往 `ACHIEVEMENT_TABLE` 加一条，`kind` 必须是
`AchievementManager.progressValue()` 已支持的类型。
