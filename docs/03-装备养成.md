## 一、四条养成轴

| 轴 | 消耗什么 | 决定什么 | 适用范围 |
|---|---|---|---|
| **局外等级** `level` 1~5 | 金币 | 基础伤害 | 武器 |
| **局内形态** `depth` 0~4 | 局内经验 | 攻击方式与 atkPct | 武器（见 [02](02-局内成长.md)） |
| **品阶** `rarity` 0~6 | 同阶装备 + 金币（+专属材料） | 强度倍率 + 镶嵌槽 + 自带属性 | 武器 / 辅助 / 防具 |
| **镶嵌 / 词条** | 属性石 / 碎片 | 属性效果 | 武器 / 防具 |

**品阶与局外等级是两条正交的轴**，都必须投入才有满强度装备 ——
这与"没有任何单一路线能点满破防"是同一条原则：让玩家始终有"还差一点"的具体目标。

### 2.1 倍率曲线为什么前缓后陡

```
青铜 1.00 → 白银 1.18 → 黄金 1.40 → 钻石 1.70 → 史诗 2.10 → 神话 2.60 → 传说 3.30
```

- 前两阶几乎白给（各 +18%），让玩家尽早尝到升阶的甜头
- 黄金→钻石出现明显断层（1.40 → 1.70），这是"高阶装备"的体感门槛
- 神话→传说只此一条路（专属材料），所以给最大的单跳（+27%）

终局 3.30 倍 ≈ 一件满级局外装备的两倍半，配合 4 个镶嵌槽与自带属性，
传说装备是"一个 build 的核心"，而不是"比神话好一点的装备"。

### 2.2 品阶自洽性校验

`validateRarityTable()` 会在配置改错时立刻报错（`RarityConfig.ts:231-257`）：
倍率必须为正且**严格递增**、镶嵌槽**不允许回退**、低于钻石不该有自带属性、
**抽奖上限不能是最高品阶**（传说必须留作进化目标）。

**三个设计决定**：

1. **专属装备没有局内进化线** —— `evolveTo` 全是 `[]`。
   常规武器的强度来自"局内形态深度"，专属武器的强度来自**品阶倍率 + 自带属性 + 镶嵌槽**。
   再给它们一条进化线会出现第三条成长轴 —— 那是复杂度堆叠，不是深度。
2. **基础伤害与同类型常规武器对齐** —— 星刃（9）≈ 铁剑（8）+1，
   虚空炮（18）= 重炮（18）。**强度来自品阶，不来自裸数值。**
   （注：代码里没有任何断言锁定这条，只是数值恰好对齐。）
3. **不进关卡推荐池** —— `AFFINITY_POOL` 只含 12 把常规武器。硬塞进去会同时破坏
   推荐/克制的战力平衡与轮转节奏。

> 📌 **没有传说级专属武器** —— 传说只能由神话升阶而来。
> 历史文档写"钻石/史诗/神话每阶每类 2 件专属防具（龙鳞铠、泰坦板甲…）"，
> **代码里根本没有"专属防具"概念**，钻石/史诗/神话/传说各 3 套都是普通套装（可抽）。

### 3.4 局外等级升级

`EquipmentManager.upgrade(equipId)`（`EquipmentManager.ts:194-214`）：

```ts
const cost = this.getUpgradeCost(equipId);
if (p.gold < cost) return false;
p.gold -= cost;
owned.level += 1;
```

> 🔴 **重大差异：`upgrade()` 只扣金币，不消耗任何材料。**
> 历史文档《品阶与升阶设计》§二 整节承诺"局外升级除了金币还要消耗 `mat_<type>` 突破材料"
> —— **这条从未实现**。连带后果见 `12-缺口与风险.md`。

### 4.3 辅助的三轴相乘

```
效果倍数 = 局外阶数倍率 × 品阶强度倍率
```

| 阶 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 倍率 | 1.00 | 1.25 | 1.55 | 1.90 | 2.30 |
| 花费 | — | 800 | 1800 | 3600 | 6800 |

一件 **5 阶 + 神话品阶**的辅助，效果是原值的 `2.3 × 2.6 = 5.98` 倍。

**为什么用倍率而不是固定加值**：辅助 effect 结构差异极大（荆棘甲给 6 点荆棘，
鹰眼镜给 6% 暴击）。固定加值会让数值型辅助随阶数平庸、百分比型线性爆炸。倍率两头都不破。

**升阶（`ascendAux`）在 `core/GachaManager.ts:880-922`，不在 ForgeManager。**
消耗同品阶辅助 × `ascendCopiesOf` + 金币 `ascendGoldOf`；**燃料不限 id**
（任意同品阶辅助都当燃料），按对象引用排除自身。**神话→传说不需要神话之核。**

|---|---|

| defense | maxHpFlat 180, shield 50, thorns 30 |
| speed | atkSpeedPct .10, moveSpd .10, rangePct .10, extraShots .15 |

### 5.5 升阶（`ascendArmor`）

消耗 **同 id（同部位）+ 同品阶** × `ascendCopiesOf` + 金币 `ascendGoldOf`
（曲线与武器**完全相同**，复用 `RarityConfig`）。**不需要神话之核。**

孔位变化：`targetLen = raritySockets(newRarity) + 3 × (newRarity - def.rarity)`
—— **每次升阶 +3 孔**。升到神话（rarity ≥ 5）时 `openedSlots = ARMOR_MAX_OPENED_SLOTS`（=9）。

### 5.6 开槽与镶嵌

| 来源 | 消耗 |
|---|---|
| 基础孔 = `raritySockets(rarity)` | 免费（品阶给的） |
| 升阶额外孔 | 每阶 +3 |
| 额外开孔 | `CRYSTAL_PER_ARMOR_SLOT` = **10 水晶/孔** |
| 神话特权 | 升到神话后免费解锁累计孔 |
| 青铜 5 套 | 还可用**突破材料**开孔（材料开孔不花水晶） |

孔位上限：`armorSlotCap = raritySockets + 3×升阶次数 + ARMOR_MAX_OPENED_SLOTS(9)`。

镶嵌 `stone_<element>`，**可卸且退还完整材料**。同属性不可重复镶。

## 六、抗性与增益如何进战斗

### 6.1 `currentResist()` —— 抗性（已接入战斗）

```ts
out = emptyResist()                            // 24 轴全 0
for each 穿戴中的 {owned, def}:
    mul = rarityPowerMul(owned.rarity)
    for e in 24 轴:
        scaled = def.resist[e] * mul
        scaled = scaled <= 1 ? scaled : scaled / (1 + scaled)   // ★ 第一次软压缩
        out[e] += scaled
for e in 24 轴:
    if out[e] > 1: out[e] = out[e] / (1 + out[e])              // ★ 第二次软压缩
```

> ⚠️ **软压缩执行了两次**（每件一次 + 求和后一次）。历史文档只描述了第一次。
> `RESIST_MAX = 0.75` 在此函数中**未被引用** —— 上限只由二次压缩隐式给出（恒 < 1.0）。

实测：万象套 4 件 × 24 轴 → `0.03 × 3.30 = 0.099`/件 → 求和 **0.3960**/轴
（不触发压缩），总 9.504。

### 6.2 🔴 `armorBonus()` —— 词条/套装/镶嵌增益（**未接入战斗**）

算法本身是完整的：

```
# (1) 单件 innate + 镶嵌石
for each {owned, def}:
    mul = rarityPowerMul(owned.rarity)
    addBonus(out, scaleBonus(def.innate, mul))      // innate 乘品阶倍率
    for el in armorSocketsOf(owned):
        addBonus(out, elementBonusToModifier(el))   // ★ 镶嵌石【不乘品阶倍率】

# (2) 套装 2/4 件
avg = 该套穿戴件的平均品阶
bonus = setBonusOf(set, avg, pieceCount)
addBonus(out, scaleBonus(bonus, rarityPowerMul(avg)))
```

> ⚠️ **镶嵌石不乘品阶倍率**，只有 innate 与套装属性乘 —— 这个不对称历史文档没写。

> 🔴🔴 **但这个函数根本没有接进战斗。**
> `GameEntry.ts:48` 只 import 了 `armorCounterBreak` / `currentResist` / `maxCounterBreak`，
> 战斗 setup（`GameEntry.ts:214,218`）只用了 `currentResist()` 与 `maxCounterBreak()`。
> `armorBonus()` 的**唯一调用点是 `ForgePanel.ts:521`（UI 展示）**。
>
> **后果：防具的单件 innate、套装 2/4 件属性、镶嵌属性石增益，在战斗中全部不生效。**
> 防具目前只提供「抗性」这一条轨。这是本项目最严重的功能缺口，见 `12-缺口与风险.md`。

### 6.3 破防 `armorCounterBreak()` 恒为 0

```ts
export function armorCounterBreak(): number { return 0; }
```

防具**完全不参与破防**（硬编码）。破防完全由武器承担，
详见 [05-属性与锻造](05-属性与锻造.md)。

## 七、武器数值如何进战斗

`EquipmentManager.buildWeapons`（`EquipmentManager.ts:280-368`）对每件武器：

```ts
rootId  = form.sources.length > 0 ? form.sources[0] : form.id   // ★ 合成产物取材料第一件
elements = socketBonusOf(rootId)        // 只读 rootId 的镶嵌
rarityMul = rarityPowerMul(ownedRarityOf(rootId))
innate   = innateBonusOfWeapon(rootId)
base     = (baseDamageOfForm(form.sources) + levelFlatAtk/n) * rarityMul
atkPct   = form.atkPct + formLevelAtkPct(st.exp) + mod.atkPct + elAtkPct + (innate.atkPct||0)
damage   = max(1, round(base * (1+atkPct) * affinityMul))
```

**品阶倍率乘在 base 上**，意味着它与形态 atkPct、天赋、镶嵌全部在同一个乘区叠加。
若乘在最终值上会出现"暴击吃两次倍率"这类难以解释的复合。

> 📌 `atkPct` 是把 5 个来源**相加**成一个数再 `(1+atkPct)`，不是各自独立乘算。
> 历史文档措辞"全部是乘算关系"不精确（语义等价，表述不准）。

### 各字段的来源不对称（实测）

| 字段 | 形态 atkPct | 镶嵌 | 自带 innate | 品阶倍率 |
|---|---|---|---|---|
| atkPct | ✔ 相加 | ✔ | ✔ | 乘在 base |
| rangePct | ✔ | ✔ | ✔ | ❌ |
| atkSpeedPct | ❌ | ✔ | ✔ | ❌ |
| critRate | ❌ | ✔ | ✔ | ❌ |
| **critMul** | ❌ | **❌** | **❌** | ❌ |
| lifesteal / extraShots / pierceResist / highHpDmg | ❌ | ✔ | ✔ | ❌ |
| **pierce** | 基数 | ✔ +N | ❌ | ❌ |

> ⚠️ **`critMul` 只来自 `mod.critMul`**（天赋 + 辅助）。镶嵌的 `ghost` 属性（critMul 0.35）
> 与任何 innate 都进不了 critMul。历史文档说 24 属性各有效果，但这一条实际不生效。

### ⚠️ 两个"基础伤害"口径不同

- `getOutGameBaseDamage()` —— 遍历**全部已持有武器**求和（含未出战的）
- `computePower().baseDamage` —— 只算**出战槽**

面板上这两个数会对不上，不是 bug 但容易误读。

## 八、万象线（隐藏养成，关闭缺口 A-6）

### 8.1 它是什么

全属性石（`stone_omni`，需 **24 种碎片各 10 个 = 240 碎片**）曾是死道具 ——
第九轮防具改为抽卡获取后，原本消费它的 `craftArmor()` 被移除。
第十一轮把它改造成**隐藏的四级养成线**，终点授予四件套「万象套」。

### 8.2 养成链

| stage | 阶段名 | 消耗 | 产出 |
|---|---|---|---|
| 0 | （未开始，隐藏） | — | — |
| 1 | 万象·碎片之核 | 全属性石 ×1 + **6000** 金币 | 进度 |
| 2 | 万象·镜胚 | 全属性石 ×1 + **12000** 金币 | 进度 |
| 3 | 万象镜甲 | 全属性石 ×1 + **24000** 金币 | 进度 |
| 4 | **万象套** | 全属性石 ×1 + **48000** 金币 | **授予 4 件传说万象套 + 自动穿戴空部位** |

**总计：4 个全属性石（= 960 碎片）+ 90000 金币** —— 全游戏最贵的一条养成线。

`OMNI_MAX_STAGE = 4`（定义在 `data/ArmorConfig.ts:323`，为避免 core→core 循环依赖）。
`OMNI_STAGE_NAMES = ['未开始','万象·碎片之核','万象·镜胚','万象镜甲','万象套']`。

### 8.3 可见性规则（"隐藏合成逻辑"）

```ts
omniVisible() = omniStage() > 0
             || (stoneBag()[OMNI_STONE_ID] || 0) > 0
             || canCraftOmni();
```

三条任一成立才可见。**未满足则 `ForgePanel` 不渲染该区块** ——
玩家在凑齐 240 碎片之前根本不知道有这条线。一旦可见就**永久可见**（stage 单调递增）。

### 8.4 万象套

| 项 | 值 |
|---|---|
| setId | `armor_wanxiang` |
| 4 件 id | `armor_wanxiang_head` / `_body` / `_pants` / `_shoes` |
| 品阶 | **6（传说）**，全部，无需再升阶 |
| 每件轴数 | **24 轴全覆盖**（与常规 92 件"每件只 1 轴"不同） |
| 每轴基准 | `OMNI_RESIST_PER_AXIS = 0.03` |
| 实测生效 | `0.03 × 3.30 = 0.099`/件 → 四件合计 **0.3960**/轴（min === max），总 9.504 |
| 与 `RESIST_MAX` 关系 | 0.396 ≪ 0.75 → **不给免疫** |
| 单件 innate | `roleInnate('element')` = pierceResist .08 / highHpDmg .08 / atkPct .04 |
| 进抽卡池？ | **否**。`allArmorPieces()` 恒 92，`poolIds('armor')` 恒 92，`wanxiang` 命中数 0 |

**"越广越薄"实测**（同口径，`currentResist()` 软压缩之后）：

| 套装 | 品阶 | 轴数 | 每轴抗性 | 总抗性 |
|---|---|---|---|---|
| 烈焰套（青铜·单轴） | 0 | 1 | 0.420 | 0.420 |
| 龙裔套（钻石·双轴） | 3 | 2 | 0.425 | 0.850 |
| 终焉套（传说·三轴） | 6 | 3 | 0.850 / 0.628 / 0.370 | 1.848 |
| **万象套（传说·全轴）** | 6 | **24** | **0.396** | **9.504** |

万象套的**每轴**抗性是最低的，但**总抗性**远超任何常规套 ——
它是终局装备，本就该是"最广但不是最厚"的通用解：追求"永远不用换装"就要付"每轴薄"的代价。

### 8.5 幂等与坏档兜底

- `grantOmniSet` 幂等（用 `id.indexOf('armor_wanxiang_') === 0` 判重）
- 满级后再调 `advanceOmni()` 返回失败，**不重复发装备**
- 拒绝条件（石不足 / 金不足 / 满级）都 `ok:false` 且**不扣任何资源**（先校验后扣费）
- 坏档兜底：`stage` 为 `'abc'` → 0、`99` → 4、`-5` → 0
- **已装备的部位不被万象套抢占**（换装权在玩家手里）

`omniPreview()` 实际返回字段：
`{ visible, stage, name, maxStage, owned, stoneHave, stoneNeed, goldNeed, canAdvance, reason }`
（历史文档写的 `needStone` / `needGold` **不存在**）
