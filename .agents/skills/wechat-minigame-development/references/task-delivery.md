# 需求、进度与交付约定

完整游戏和跨模块任务使用以下约定。小修复只需明确预期行为并做相关验证，不必生成全套计划或额外文档。

## 目标与验收

先从现有信息确定游戏核心循环、用户本轮目标、包含的功能及重要边界。把需求写成玩家可观察、开发可检查的条件；避免仅用“完整”“流畅”“好看”作为验收标准。

可使用以下精简映射，规模小则在回复中表达即可：

| 需求 | 可观察的验收条件 | 实现位置 | 验证方式与状态 |
|---|---|---|---|
| 结算奖励 | 胜利入账一次，连点与重进不重复发放，重启后保留 | 对局流程、奖励、存档、结算 UI | 逻辑测试 + 实际对局；逐项记录是否执行 |

区分“用户明确要求”“根据当前工程推断”“暂定方案”。只对会改变产品方向或实现成本的关键问题提问；合理默认值说明后即可推进。玩法方案应说明玩家为什么操作、失败后如何继续、获得什么反馈，而非只有系统和类的列表。

## 需求变化

用户的新消息通常修正当前任务。先判断改变的是目标、范围、表现还是验收条件，再更新相关工作；除非用户明确取消，不丢弃原有目标。

修改已有玩法时检查关联入口、配置、UI 文案、经济产出/消耗、存档、教学和回归测试。根据实际影响处理，不为每个任务机械检查全部系统。旧代码反映现状，不能成为拒绝实现新需求的理由；官方能力限制则应明确解释并提供接近目标的可行选择。

## 分阶段推进

完整开发以可试玩结果划分阶段，例如“一局可完成 → 成长与重玩接通 → 最终表现与平台接入 → 发布验证”。每阶段给出可检查的结果，不用堆积未接线的模块数量充当进度。

需求已足够时直接开发。计划不是额外的审批关卡，也不因为达到内部里程碑就停下已授权的任务。小范围的实现选择由 Agent 决定；影响付费、账户或产品方向的选择按已有授权和用户偏好处理。

发现现有缺陷时，先判断它是否阻塞本轮目标。必要修复一并完成；无关问题记录到缺口文档，避免在功能任务中悄悄重写架构、重做经济体系或添加商业化能力。

## 跨会话保存进度

仅在任务较长、涉及多个里程碑或需要交接时维护项目根目录的 `.agents/project-state.md`，保存当前状态而非完整聊天记录：

- 当前目标和有效范围，用户明确的关键选择及重要假设。
- 里程碑与验收条件、已完成行为和对应实现位置。
- 已执行检查的日期、版本/设备等必要条件与结果；待验证项单列。
- 外部依赖、具体阻塞及下一步可执行动作。

不记录密钥和个人信息；不创建空文件等待填写。恢复开发时以当前文件、工作区改动及可核验证据更新状态，不能把旧“已通过”当作新版本结果。这里保存任务状态，模块说明仍按 `docs/00-文档索引.md` 维护，未实现功能与长期风险仍归 `docs/12-缺口与风险.md`，不要复制多套待办。

## 结束前对照

逐项确认本轮需求是否有实现和验证依据，状态可表述为“已实现且已验证”“已实现待特定环境验证”“因明确依赖尚未实现”或“不适用”。不能把模拟成功、测试桩通过、预览通过与微信真机可用合并成一个“完成”。

最后检查实际改动、入口与调用链、必要配置、遗留占位和相关文档。交付说明聚焦用户现在可以做什么、用什么证据验证、还剩什么；未执行的命令和外部步骤不写成成功。

需要用户介入时说明具体字段、工具页面或操作以及它阻塞的验收项。重复利用已获得的配置和授权，不反复询问同一问题；继续完成不依赖该步骤的工作。
